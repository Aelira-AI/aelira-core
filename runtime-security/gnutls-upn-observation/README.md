# Native Windows UPN name-constraint observations

This finite comparison records Windows certificate-chain and BASE-policy results for eight synthetic UPN cases. It supports the GnuTLS name-constraint compatibility investigation in #582. It does not change GnuTLS, its original acceptance matrix or any release gate.

The frozen fixture directory contains thirteen public DER certificates, their hash manifest and the inspected SAN/name-constraint bytes. It contains no private key, PEM or CSR. `verify-inputs.ts` binds the entire reviewed manifest and DER inspection to fixed external hashes, verifies the exact file closure, all signatures and validity at the fixed common time. `test-inputs.ts` first accepts those real inputs, then rejects modified metadata, modified DER, missing and extra members.

`generate.ts` documents how fresh synthetic preparation can be made in a new private scratch directory with OpenSSL. That directory also contains generated keys and signing inputs. Only explicitly selected public DER and JSON files may be exported. New generation does not replace these frozen fixtures or become an accepted oracle automatically. `inspect-der.ts` records the actual bounded DER payloads before comparison.

The native observer requires Windows x64 and Bun 1.3.14. It creates separate in-memory root/issuer stores and a fresh chain engine for each case. The only anchor is the synthetic self-signed root. It disables AIA and root auto-update, uses cache-only URL retrieval, requests serverAuth and applies BASE policy with zero ignore flags. No revocation checking or hostname policy is requested. No certificate is installed into an account or system store.

Both unconstrained UPN leaves must first have clean exact three-certificate paths. Each subsequent result retains construction and policy API booleans, aggregate/simple/element error and information masks, exact ordered DER hashes and policy error locations. An API, path, time, root or usage failure is evidence of an experiment failure, rather than a name mismatch. `observed` means all eight observations completed; it does not mean Windows agrees with the unchanged GnuTLS expectations.

CI checks the exact public Git checkout and frozen inputs, pins Bun, then creates a temporary outbound-block rule on the disposable Windows VM. The firewall service and effective profiles must already be enabled, with no disabled-interface exclusions. An online positive precedes the blocked network control. The observer runs only after full effective enforcement and broad protocol/port/address/application scope are verified. Child execution, termination and output waits are bounded. The rule is removed in a finally block; a successful effective-policy query must confirm absence, followed by a restored online control before artifact upload. Full receipts bind the commit/tree, source hashes, VM image identifiers, Bun executable hash, OS/DLL versions and the actual firewall/network controls. A failed isolation control prevents the experiment.

The observations can distinguish excluded-UPN handling from unsupported-name constraints for these exact ASCII cases. They do not establish universal Unicode, case, suffix, multiple-name, self-issued or permitted-set intersection behavior. GnuTLS component acceptance still requires a supported semantic repair, both native Linux architectures, independent review and every final installed copy.

The broad all-profile rule may report both Full and InactiveProfile. CI preserves this actual array and refuses every other state. It also creates a separate block for each actual active profile and requires only Full for each one. The active profile mask must remain unchanged around the experiment, and all temporary rules must be absent after restoration. This separates inactive profiles from failed enforcement without relying solely on a failed network request.

Primary API contracts: [chain construction](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain), [exclusive chain-engine stores](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_chain_engine_config), [BASE policy](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certverifycertificatechainpolicy), and [Bun FFI](https://bun.sh/docs/runtime/ffi).
