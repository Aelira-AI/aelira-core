### Changed

- CI: each native LaTeXML capture attempt now records a bounded refusal class in its public attempt receipt (`aelira-latexml-capture-attempts-v4`): `upstream_http_auth` for a 401/403 from the snapshot host, `upstream_http_5xx`, `upstream_http_4xx`, `upstream_http_other`, `transport`, `timeout`, `tls`, `integrity` or `unknown`. The job summary prints each attempt's exit, retry eligibility and class, so a red run shows whether the refusal came from upstream. No URL, header or body is recorded. Refusals that APT reports are `unknown`, because APT's exit does not identify an HTTP cause. Retry eligibility and gating are unchanged. Refs [#737](https://github.com/Aelira-AI/aelira-core/issues/737).

- The dashboard labels a recorded change whose finding the saved-file rescan no longer detects "Change applied · finding no longer detected" instead of "Change applied · automated check passed", and adds " · human review required" when the record says the change needs review. The rescan shows that a finding is no longer detected, not that the change is correct, and the earlier label read as an approval. Records with no saved-file verification still read "Change applied · verification not reported" ([#693](https://github.com/Aelira-AI/aelira-core/issues/693)).
- **Breaking:** `aelira scan web --format json` now prints the finished scan detail from `GET /education/scans/{scan_id}` instead of the acknowledgement of the queued scan, and `aelira export` names its date column `date_utc` instead of `date`. Scripts that read either need updating ([#775](https://github.com/Aelira-AI/aelira-core/issues/775)).
- CLI: `scan web --batch` takes the URLs to scan as arguments or from a `--urls-file` (one per line, `#` comments allowed) and sends them as the `urls` list the API accepts, with a new `--depth` option for `max_depth`. The API's default depth of 1 also scans the pages each URL links to, and `--depth 0` scans only the given URLs. `--max-pages` now applies to sitemap scans only, and several URLs without `--batch` are refused ([#775](https://github.com/Aelira-AI/aelira-core/issues/775)).
- CLI: `aelira interactive` no longer clears the terminal. It always prints a plain-text line with the tool's name and version, and shows the decorative block-character logo only on an interactive terminal when none of `NO_COLOR`, `TERM=dumb`, a CI environment, `AELIRA_NO_BANNER` or the new `--no-banner` flag applies, because screen readers read the logo's characters out one by one. `aelira ci` now also treats truthy `CI` values such as `CI=1` as CI ([#770](https://github.com/Aelira-AI/aelira-core/issues/770)).
- CLI: console output labels automated scores "Scanner score" instead of "Compliance Score" or "Accessibility Score", and emoji are removed from terminal output, where screen readers read them aloud by name; where a symbol was the only signal it is replaced with words. JSON field names are unchanged ([#772](https://github.com/Aelira-AI/aelira-core/issues/772)).
- CI: the Canvas LMS user journey passes optional basic-auth credentials (`AELIRA_JOURNEY_CANVAS_GATE_USERNAME` and `AELIRA_JOURNEY_CANVAS_GATE_PASSWORD`) to the Canvas origin only, so the journey can run against a Canvas instance behind HTTP basic auth. When they are unset nothing changes ([#789](https://github.com/Aelira-AI/aelira-core/issues/789)).

### Security

- The Pa11y runtime forces zod to 4.6.7 to clear [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) (CVE-2023-54404, high), which affects every zod before 4.6.6 and has no zod 3 fix. Pa11y 9.0.1's `chromium-bidi` 14 was written for zod 3. Under zod 4 it still parses valid WebDriver BiDi commands, but its validation of invalid input throws a TypeError instead of a BiDi error. Pa11y drives Chrome over the Chrome DevTools Protocol, which `config/pa11y.json` now pins, so `chromium-bidi` is not loaded during scans. The Pa11y smoke gate checks the protocol, checks that a real scan never loads `chromium-bidi`, and checks that its parser still loads with the overridden zod. The clean fix, pa11y 10, is tracked for a later release in [#786](https://github.com/Aelira-AI/aelira-core/issues/786). Details: [docs/security/pa11y-zod-override-0.10.0.md](docs/security/pa11y-zod-override-0.10.0.md) ([#785](https://github.com/Aelira-AI/aelira-core/issues/785)).
- `filelock` moves from 4.1.1 to 4.2.4, which fixes CVE-2026-112906, CVE-2026-112907, CVE-2026-112913, CVE-2026-112914, CVE-2026-112937 and CVE-2026-112940 (fixed in 4.2.1); it comes in through `huggingface_hub` for the transcription models. The application's `setuptools` moves from 84.0.0 to 84.2.1, which fixes GHSA-xmj3-9gf7-h52w (fixed in 84.1.0), a path escape through `namespace_packages.txt` during legacy wheel installation on Windows. The final-image package check now requires `setuptools` 84.2.1 in the runtime and developer environments. The build-only `setuptools` 84.0.0 wheels that the native lxml, psycopg2 and Pillow evidence recipes pin by hash are not shipped and are unchanged.
- The API and development images install Debian's fixed `libbrotli1` `1.1.0-2+deb13u1` (DSA-6582-1) for CVE-2026-111497, a critical buffer overflow in the Brotli decoder that libcurl, FreeType and libheif load. An interim rebuild of Debian's `brotli` source with the same upstream fix ([#774](https://github.com/Aelira-AI/aelira-core/issues/774)) was retired once Debian's update arrived, because the update sorts above it. The Pa11y scanner's Node.js v24.22.1 compiles in its own Brotli and already includes the fix. The work left lasting improvements in the rebuild framework used for libxml2, libX11 and libXrender:
  - a rebuilt version may keep Debian's binNMU suffix;
  - a recipe can run the package's own build-time tests;
  - any installed package from a rebuilt source that is not at the rebuilt version is refused;
  - builds are reproducible: each source builds under a fixed path, package file times are clamped to the recipe's changelog date, and a `reproducible` recipe is built twice and must produce identical packages.
- The API image no longer installs Debian's `ffmpeg` package. The `ffmpeg` and `ffprobe` programs the application runs now come from the image's own build of the hash-verified FFmpeg 9.0.2 release under `/opt/ffmpeg9`, the build PyAV and OpenCV already link, and are linked from `/usr/local/bin` so every call site behaves as before. The build compiles in only the `file` and `pipe` protocols, so no network protocol exists to reach even without the application's input whitelist. It links Debian's `libmp3lame0` and `libvorbis` so spoken audio is still written as MP3 and Ogg Vorbis. Removing the package removes 110 Debian packages, among them Debian's FFmpeg 7.1.5 libraries, `librist4` and its `libcjson1` dependency, `libsndfile1`, `libssh-4`, `libsrt1.5-gnutls`, SDL and PulseAudio, which shrinks the arm64 image by about 158 MiB, and retires 22 unfixed-advisory dispositions: 16 for FFmpeg, 5 for cJSON and 1 for libsndfile. Debian's tracker records the 16 FFmpeg advisories as fixed in its FFmpeg 9.0.2 package; the in-house build is not a distribution package, so the image scanner no longer reports on it. The final-image checks fail if any removed package returns, or if the programs on PATH differ from the pinned build's version, configure line, library paths, protocols or encoders. A new image-level test, `scripts/smoke_media_cli.py`, runs every ffmpeg and ffprobe call site against the shipped programs on small hash-pinned fixtures, because the existing real-ffmpeg tests use the CI runner's own ffmpeg. The Docker CI job also fails when a disposition names a package the image does not install. The FFmpeg DASH step leaves the libxml2 consumer check, since the new build does not link libxml2. The development image keeps Debian's `ffmpeg` as its fixture tool ([#748](https://github.com/Aelira-AI/aelira-core/issues/748), [#739](https://github.com/Aelira-AI/aelira-core/issues/739)).
- The API and development images rebuild Debian trixie's `libxml2`, `libx11` and `libxrender` source packages with upstream and Ubuntu security fixes, because Debian has no fixed trixie packages. `libxml2` `2.12.7+dfsg+really2.9.14-2.1+deb13u3+aelira2` carries Canonical's Ubuntu 24.04 patches for CVE-2026-6653, CVE-2026-74860, CVE-2026-86138, CVE-2026-86140, CVE-2026-86142, CVE-2026-86143 and CVE-2026-86144. `libx11` `2:1.8.12-1+aelira1` carries the libX11 1.8.14 commits for CVE-2026-88806, CVE-2026-94283, CVE-2026-94284 and CVE-2026-94285, and `libxrender` `1:0.9.12-1+aelira1` carries the libXrender 0.9.13 commit for CVE-2026-88807. CVE-2026-86139 is recorded as not affected, because the 2.9.14 source Debian ships already rejects the zero length the advisory describes. The single-advisory CVE-2026-6653 rebuild is generalised into one recipe format (`docker/debian-backports/`): every source file is authenticated through Debian's or Ubuntu's signed archive index and pinned by hash; every patch must apply with no fuzz and only reviewed offsets; and each build writes a receipt listing every input, patch, package and library hash and the CVEs fixed. The image check (`scripts/verify_debian_backports.ts`, which replaces `verify_libxml2_6653.ts`) binds the receipts to the installed packages, loaded libraries, native consumers and image layers. The inventory gate accepts a scanner row as patched only for that exact rebuilt package version, which replaces the hard-coded CVE-2026-6653 exception. Behavioural controls run in every build for CVE-2026-86144, CVE-2026-88806, CVE-2026-94285 and CVE-2026-88807: each passes on the patched code and fails on Debian's stock library or with only the upstream guard removed. The 2 to 4 GiB triggers of CVE-2026-86138, 86142 and 86143, and the XIM-server triggers of CVE-2026-94283 and 94284, are covered by patch application and source review only. The record is [docs/security/debian-backports-0.10.0.md](docs/security/debian-backports-0.10.0.md) ([#579](https://github.com/Aelira-AI/aelira-core/issues/579), [#605](https://github.com/Aelira-AI/aelira-core/issues/605), [#739](https://github.com/Aelira-AI/aelira-core/issues/739)).
- The application's `certifi` moves from 2026.7.22 to 2026.10.19. Earlier versions include the `emSign ECC Root CA - G3` root, and eight intermediate CAs that chain to it have compromised private keys ([GHSA-6q48-6c7w-9gw2](https://github.com/advisories/GHSA-6q48-6c7w-9gw2)), so someone holding one of those keys could issue a certificate for any hostname and intercept TLS from clients that trust the `certifi` bundle, which includes the application's outbound HTTP through `httpx`. `certifi` 2026.10.19 removes that root and keeps the three emSign roots that are not affected ([#723](https://github.com/Aelira-AI/aelira-core/issues/723)).
- The quickstart and developer images install pip 26.2.2 instead of 26.2.1, because the `certifi` that pip vendors moves from 2026.6.17 to 2026.10.19, and the final-image package check requires the exact vendored manifest of the published 26.2.2 wheel. The runtime and developer images also stop trusting `emSign ECC Root CA - G3` in the system store, which `curl`, Python's default SSL context and the Hugging Face Hub client read. Debian trixie's `ca-certificates` 20250419 ships it and the security update 20250419+deb13u1 removes it, but images built from an older package index still install 20250419, so the build deselects that one root in `/etc/ca-certificates.conf` and rebuilds `/etc/ssl/certs`. The other emSign roots stay trusted, and the step does nothing once the installed package no longer lists the root. The final-image check fails if the bundle or any certificate or hashed link in `/etc/ssl/certs` has the root's SHA-256 fingerprint, or if one of the three unaffected emSign roots is missing. The build-only pip 26.2.1 pins in the native evidence pipelines are unchanged and are not shipped. Node.js keeps its own built-in root store, which the move to Node 24.22.1 below removes the root from ([#725](https://github.com/Aelira-AI/aelira-core/issues/725), [#726](https://github.com/Aelira-AI/aelira-core/issues/726)).
- The dashboard's `follow-redirects` moves from 1.16.0 to 1.16.1, a production dependency through `axios`. Version 1.16.0 is affected by two high-severity advisories: array-form headers bypass cross-origin credential stripping ([GHSA-q3jh-wrc6-jgq8](https://github.com/advisories/GHSA-q3jh-wrc6-jgq8)), and `sensitiveHeaders` regex escaping can expose credentials ([GHSA-8r9p-f939-6h3c](https://github.com/advisories/GHSA-8r9p-f939-6h3c)). Only the lockfile entry changes ([#721](https://github.com/Aelira-AI/aelira-core/issues/721)).
- Pillow moves from 12.3.0 to 13.0.0, the first release with fixes for nine advisories that affect 12.3.0: GHSA-8g5g-8vmr-9782 (critical, heap buffer overflow in the JPEG decoder), GHSA-58r4-6rv3-gfh8 (out-of-bounds access in `ImageMorph` on a zero-width image), GHSA-65qm-jvmh-6pqg (GIF seeking keeps an image size that the decompression bomb check rejected), GHSA-c6hw-5grf-ff96 (out-of-bounds read in the TIFF tile and RGBA decoding paths), GHSA-p4wg-p73j-c528 (unbounded recursion when parsing a PDF page tree or trailer chain), GHSA-pchr-8j38-3x4p (the TIFF encoder reads past a ColorMap of the wrong size), GHSA-q45j-58j2-45rg (uninitialised memory returned as pixels for short JPEG strips in TIFF files), GHSA-462x-pgg6-55fp (the tiled TIFF decoder reads past its tile buffer) and GHSA-vx6w-vv9f-6gvg (EPS `load(scale)` renders past the decompression bomb limit). Images that users upload reach these decoders, including images embedded in PDF, Word, PowerPoint and Excel files. The API image still builds Pillow from its hash-verified source release against libtiff 4.7.2 and Debian's image libraries. Pillow 13 is also stricter with malformed images: a PNG with a truncated `cHRM` chunk, which 12.3.0 decoded, is now rejected as an invalid image. It no longer writes 32-bit greyscale images as PNG, so the Word, PowerPoint and Excel scanners convert such embedded images to 16 bits first, which produces the same PNG as before ([#729](https://github.com/Aelira-AI/aelira-core/issues/729)).
- pypdf moves from 6.20.1 to 6.21.2. Versions before 6.21.1 open image data that claims the `/DCTDecode` filter with any Pillow image plugin instead of only the JPEG one, so a crafted PDF could reach other image parsers ([CVE-2026-113786](https://github.com/advisories/GHSA-5hx5-vpf9-5wcv)). The application uses pypdf only to extract text and count pages, and does not read page images through it. 6.21.0 through 6.21.2 also add limits on stream, field and cross-reference parsing work, and the existing text extraction and page count paths already treat a parsing error as an incomplete check. brotli moves from 1.2.0 to 1.2.1, which fixes an out-of-bounds write in the decoder that a crafted compressed stream could use to corrupt memory and possibly run code ([CVE-2026-111497](https://github.com/advisories/GHSA-9v8h-qqgm-4m35)). httpx and requests use it to decode Brotli responses on outbound fetches. The native consumer fixture pins pypdf to the same version ([#743](https://github.com/Aelira-AI/aelira-core/issues/743)).
- Six ImageMagick advisories without a Debian fix are reviewed and disclosed in [known unfixed advisories](docs/security/known-unfixed-advisories-0.9.12.md#imagemagick-advisories-published-after-the-0913-candidate-review). CVE-2026-106576, a slow rational conversion when an image with a crafted XMP profile is written, is affected: LaTeXML can rewrite submitted PNG and JPEG graphics, so a document can cause a denial of service bounded by the post-processing timeout. CVE-2026-106573 and CVE-2026-106578 (MVG decoder), CVE-2026-106579 (bypass of coder-domain policy rules) and CVE-2026-106580 (CUT palette load) are not affected, because those coders are selected only by an explicit format prefix or file extension and submitted content can supply neither. CVE-2026-107209 (RSVG decoder) is not affected because the image has no ImageMagick SVG coder module. The native image check now also fails if an SVG, MSVG or RSVG format or an ImageMagick `svg` module is present, or if a `.png` file holding MVG commands is decoded without an explicit `mvg:` prefix ([#743](https://github.com/Aelira-AI/aelira-core/issues/743)).
- PyMuPDF moves from 1.28.2 to 2.0, which bundles MuPDF 1.28.5 instead of 1.28.2. By their commit subjects, the 141 upstream commits in between include fixes for out-of-bounds writes in JPEG loading, cached glyph painting and TrueType collection conversion, a double free in `find_most_recent_common_ancestor`, and overflows in CFF subsetting. [CVE-2026-92413](https://nvd.nist.gov/vuln/detail/CVE-2026-92413), a null dereference in `pdf_open_filter`, is expected to be fixed in that range, but the fix commit was not confirmed in the 1.28.5 build. PyMuPDF 2.0 also fixes a path traversal in its command-line font extraction ([CVE-2026-82035](https://nvd.nist.gov/vuln/detail/CVE-2026-82035)), which the application never invokes. The wheel still bundles zlib 1.3.2. Behaviour changes: PyMuPDF 2.0 requires Python 3.11 or newer and warns on `import fitz`, so the one test that used that name now imports `pymupdf`; its wheel embeds a layout model that gates `Page.find_tables()` unless `use_layout=False` is passed, so table detection and table writing now pass that argument and keep the same line-based finder as 1.28.2 (the model dropped ruled tables from the PDF test fixtures and adds roughly 0.4 seconds and 90 MB at import); it declares `pymupdf-layout`, `pymupdf4llm`, `networkx` and `tabulate` as dependencies, which are now pinned in `requirements.txt` (150 to 154 runtime entries); and closing an already closed document now raises, so remediation cleanup skips handles that a no-save exit path has already closed. The PDF test files pass with the same failures as before the upgrade, and the synthetic PDF acceptance corpus produces identical results and output bytes apart from one XMP timestamp. Refs [#742](https://github.com/Aelira-AI/aelira-core/issues/742).
- Remaining after the PyMuPDF upgrade, disclosed and tracked in [#755](https://github.com/Aelira-AI/aelira-core/issues/755): [CVE-2026-112036](https://nvd.nist.gov/vuln/detail/CVE-2026-112036), a double free in MuPDF's `free_char_list` (`pdf-xref.c`). NVD lists it as affecting MuPDF through 1.28.5, so PyMuPDF 2.0 does not fix it. It is reachable only for a PDF whose signature fields carry `/Lock` dictionaries and is rated 4.3. FreeType 2.14.3 ([CVE-2026-95512](https://nvd.nist.gov/vuln/detail/CVE-2026-95512), [CVE-2026-50811](https://nvd.nist.gov/vuln/detail/CVE-2026-50811)) and MuJS ([CVE-2026-110715](https://nvd.nist.gov/vuln/detail/CVE-2026-110715)) are also bundled in MuPDF; the versions inside the 1.28.5 build were not verified, so those advisories are not marked fixed.
- The API image replaces Debian's open ImageMagick policy and delegate list. ImageMagick runs only inside LaTeXML, which reads PNG, JPEG, EPS and PDF graphics and writes PNG and JPEG files, so the new `policy.xml` denies every format and then allows only those, plus the PAM files Ghostscript produces for CMYK documents. It allows only the Ghostscript program as a delegate, denies filters, `@` file lists and URL reads, and lowers the image size, memory, disk and thread limits. The LaTeX tool environment sets `MAGICK_TIME_LIMIT=50`, because ImageMagick 7.1.1-43 applies a policy time limit only as a cap. The new `delegates.xml` keeps only the two Ghostscript rendering delegates, both run with `-dSAFER -dBATCH -dNOPAUSE`. Before this change, a file named `.png` holding a PostScript program was rendered through Ghostscript inside LaTeXML, and the MSL, MVG, CUT, TEXT and PS coders read files when named with a prefix or extension. The native image check now converts EPS, PDF, PNG and JPEG graphics through LaTeXML, checks every Ghostscript command line, and fails if any of those reads, an oversized image or a changed policy file is accepted, with a control for each refusal. CVE-2026-106576 stays affected: no policy rule covers embedded XMP profiles, and the time limit is not checked inside the slow conversion; the [disclosure](docs/security/known-unfixed-advisories-0.9.12.md#imagemagick-advisories-published-after-the-0913-candidate-review) names the upstream fix. LaTeX tools now run with a new, empty home directory outside their conversion directory, which they can neither read nor write, so a policy file planted under the conversion directory's `.config/ImageMagick` is no longer read; ImageMagick reads such files after the system policy and a later rule wins. The CVE-2026-106579 disposition now rests on the deny-all coder rule ([#749](https://github.com/Aelira-AI/aelira-core/issues/749)).
- Two further ImageMagick advisories with no Debian fix are reviewed against the same policy. CVE-2026-106565, a missing EOF check that makes reading bzip2-compressed image data loop forever, is not affected: ImageMagick unwraps a gzip or bzip2 file by its leading bytes before any coder or policy check, so the policy cannot refuse a `.png` or `.jpg` whose bytes are a bzip2 stream, but the converter now checks every file the `latexml` and `latexmlpost` stages can read, whatever its name, and refuses the stage with `compressed_input` before LaTeXML starts if any file begins with a gzip, bzip2, xz or zstd magic; uploaded LaTeX projects refuse such a member with `compressed_member`. No accepted LaTeX input type starts with these bytes, except a text file whose first three characters are literally `BZh`, which is refused with the same reason. The library fix is tracked in [#750](https://github.com/Aelira-AI/aelira-core/issues/750). CVE-2026-106567, a PSD resource-block loop, is not affected: the upstream fix shows it happens on 32-bit builds only, the image is 64-bit, and the policy denies the PSD coder anyway. The native image check now also generates a benign bzip2-wrapped PNG, a benign BZip MIFF and a benign PSD under a permissive test policy and asserts that MIFF and PSD are refused by prefix, extension and content sniffing, that the converter refuses a bzip2- and a gzip-wrapped PNG before LaTeXML runs while the plain PNG converts, and that the bare launcher without that check still renders the wrapped file ([#749](https://github.com/Aelira-AI/aelira-core/issues/749)).
- The API and developer images' Pa11y runtime moves from Node 24.21.0 to 24.22.1, the 2026-10-21 security release for CVE-2026-105481, CVE-2026-105482, CVE-2026-105483, CVE-2026-106069, CVE-2026-106073, CVE-2026-106074 and CVE-2026-111497, which also carries OpenSSL 3.5.9. Both Dockerfiles pin the `node:24-bookworm-slim` multi-arch index digest `sha256:55fb5f5a527ea2c5c4a95f963e48ef90aa38c7b346054fdc8ee9957a2b55d205`, which resolves to 24.22.1 on linux/amd64 and linux/arm64, and the Pa11y smoke gate that runs when each image is built now rejects an older Node or an OpenSSL below 3.5.9. The Playwright Python package moves from 1.64.0 to 1.64.1, whose bundled driver is Node 24.22.1 instead of 24.21.0, and the dashboard and CLI lockfiles follow. The dashboard image's `node:22-alpine` stage only builds static files for nginx and ships no Node runtime, so it is unchanged ([#745](https://github.com/Aelira-AI/aelira-core/issues/745)).
- Node 24.22.1's built-in root store no longer includes `emSign ECC Root CA - G3`, the root whose intermediate CAs have compromised keys ([GHSA-6q48-6c7w-9gw2](https://github.com/advisories/GHSA-6q48-6c7w-9gw2)). Pa11y makes its HTTPS requests through that store, and Node 24.21.0 still trusted it, so the gap in [#726](https://github.com/Aelira-AI/aelira-core/issues/726) closes with the new base image. Measured on both versions, `tls.rootCertificates` held 121 roots including all four emSign roots on 24.21.0 and 118 roots with only `emSign Root CA - G1` among them on 24.22.1. `scripts/verify_final_os_packages.py node-trust-store` now reads that list from the image's Node by SHA-256 and fails the build if the distrusted root returns or the store loses `emSign Root CA - G1`. The production image runs it with the other checks and the developer image and the quickstart CI job run it by name ([#726](https://github.com/Aelira-AI/aelira-core/issues/726)).
- The scanner's browser is now a hash-pinned Chrome for Testing 156.0.8078.47 instead of the Chromium inside Playwright. Playwright 1.64.1 bundles 156.0.8078.4 and the 1.65 prerelease 156.0.8078.12, and Chrome stable 156.0.8078.47 (2026-10-20) fixed many CVEs published that day, so no Playwright release had them. `scripts/chrome-for-testing.json` records the version and, for linux/amd64 and linux/arm64, the archive size and SHA-256; `scripts/install_chrome_for_testing.py` downloads the archive over HTTPS, rejects anything that differs from the pin, and refuses archive entries that escape the destination or are symlinks. The API and developer images unpack it at `/opt/chrome-for-testing/chrome` and no longer install Playwright's Chromium. The web scanner, focus-order and deterministic axe checks, equation verifier and LaTeX HTML-to-PDF fallback pass that executable to Playwright through `AELIRA_CHROMIUM_EXECUTABLE`, Pa11y reaches it through its existing launch path, and a configured path that is not a file is an error instead of a fallback to the bundled browser. The image-build smoke gate fails unless Pa11y and a Playwright launch both report 156.0.8078.47. The deterministic Chromium release smoke and the browser journey jobs in CI install and run the same pinned build, and the dashboard Playwright configs and the CLI pick it up from the same variable ([#746](https://github.com/Aelira-AI/aelira-core/issues/746)).
- `pypdfium2` stays at 5.14.0, the newest release, which bundles PDFium 156.0.8076.0, before the 156.0.8078.47 fix for CVE-2026-113022 (PDFium memory corruption). No release with a fixed PDFium exists, so this advisory stays open. Uploaded PDFs reach PDFium through OCRmyPDF, whose default rasterizer uses `pypdfium2` when it is installed; `pdfplumber` imports it only to draw page images, which Aelira never requests. [`docs/DEPENDENCIES.md`](docs/DEPENDENCIES.md) records the disposition and the option of forcing OCRmyPDF's Ghostscript rasterizer, which changes OCR input and needs its own decision ([#747](https://github.com/Aelira-AI/aelira-core/issues/747)).

### Fixed

- CLI: `aelira scan pdf`, `docx`, `xlsx`, `ppt`, `code` and `latex` printed `File: Unknown` and `N/A` with no score, counts or scan ID, wrote CSVs with no finding rows, and `aelira export` wrote only a header, because they read at the top level fields that the scan detail nests under `scan` and `scan.result`. They now read the nested response, show unknown values as unknown rather than zero, and drop lines for fields the API never returns. JSON output is unchanged ([#772](https://github.com/Aelira-AI/aelira-core/issues/772)).
- CLI: `aelira scan web` and `aelira scan watch` now wait for each scan to finish and report its real results. They used to read the acknowledgement of the queued scan as the result, so `scan web` printed `URL: Unknown` and ended before anything was scanned, and `scan watch` reported every file as `0 issues` with a score it computed locally. `scan web --batch` was rejected by the API with a 422. `scan watch` no longer invents a score for local HTML checks, and those checks now open a browser context, without which every page was refused. The commands wait up to 5 minutes for a page or file and 30 minutes for a sitemap or batch ([#775](https://github.com/Aelira-AI/aelira-core/issues/775)).
- Generated alt text that contains line breaks or tabs is now folded into single spaces instead of being discarded. Vision models describe tables, lists and multi-part figures over several lines, and the shared alt text check rejected any control character, line breaks included, so those descriptions were thrown away and the image was left undescribed. Line breaks (including U+2028 and U+2029) and tabs now become single spaces, repeated whitespace collapses, and the length limit applies to the folded text. Every other control, format or surrogate character, including NUL, form feed, zero-width characters and bidirectional controls, still causes the description to be rejected. HTML remediation still leaves multi-line model replies for ARIA labels, form labels and language codes to a human, since those are single-line values, and Canvas image descriptions are written in their normalized form ([#711](https://github.com/Aelira-AI/aelira-core/issues/711)).
- Transcripts no longer label speakers. Captions, transcripts and stored segments used to carry invented `Speaker N` and name labels, produced by a pause-and-wording heuristic rather than voice identification, so one voice could appear as several people in WebVTT `<v>` spans and SRT prefixes. Segments now have no speaker unless real speaker diarization supplies one, which this product does not run. Captions and transcripts stored by earlier scans keep their labels until the media is scanned again ([#649](https://github.com/Aelira-AI/aelira-core/issues/649)).
- Equation canonicalisation no longer treats a LaTeX brace group around a single item as part of the meaning, so `x^{2}` and `x^2` canonicalise identically and handwritten equation agreement no longer sends them to manual review because of braces alone. Different readings still differ, and a group around a lone operator or around several factors is kept. The canonicaliser also accepts binomial coefficients (`\binom`, `\dbinom`, `\tbinom`): `linethickness` is allowed on `mfrac` only, and `mstyle` is allowed with only `displaystyle` and `scriptlevel`, which also admits `\dfrac`, `\tfrac`, `\cfrac` and the `\displaystyle` family; an `mstyle` that carries colour or size (`\color`, `\large`) is still rejected. Compatibility: the canonical MathML form is now version 2 and the handwritten consensus policy is `handwritten-equation-consensus-v2`. Handwritten equation evidence stored by earlier versions, and printed-equation contracts whose stored MathML contained a collapsible group, now read as invalid contracts and block approval. Operator action: run remediation again on the affected documents to regenerate those findings. No database migration is involved ([#691](https://github.com/Aelira-AI/aelira-core/issues/691), [#690](https://github.com/Aelira-AI/aelira-core/issues/690)).
- An equation whose rendering is larger than the verifier's size bound is now reported with its own reason, `equation_too_large_for_verification`, instead of the generic `equation_verification_failed`, which surfaced only as an unrecorded manual reason. The finding stays manual and now carries an explanation that the recognized equation renders larger than the automatic check supports, with next steps. Every other verifier failure, including a renderer crash, keeps its existing reason. This reports the limit and does not raise it ([#692](https://github.com/Aelira-AI/aelira-core/issues/692)).
- A printed equation is now staged for review only after a blind second reading agrees with the first. Printed equations, both embedded images and scanned regions, were verified by rendering one reading and comparing the render with the source crop. That is a visual similarity filter, not an equivalence proof, and a reading one symbol away from the image could be staged, for example `x^{3} + 3x - 7 = 0` for `x^{2} + 3x - 7 = 0`. After the visual check passes, a second reader now transcribes the same image in a separate call with its own pinned prompt and without the first reading, both readings are reduced to canonical MathML (version 2), and they must be exactly equal; a reading the visual check rejects costs no second call. When the second reading is unavailable, fails, declines or disagrees, the finding stays manual with the reason `printed_equation_verifier_unavailable`, `printed_equation_verifier_failed`, `printed_equation_verifier_declined` or `printed_equation_semantic_disagreement`. The agreement is recorded as consensus evidence in the review contract (policy `printed-equation-consensus-v1`, the digests of both readings and the provider and model of each), and a printed-equation contract now requires it. The recognizer and the second reader now ask the provider for enough tokens to finish a reading of the longest accepted length, where a fixed 500 cut long equations off so that they stayed manual, and an answer replayed from the provider's cache, which names no model, is refused as evidence, for the handwritten readers as well. Matching readings can both be wrong, so human approval is still required before download or write-back. Compatibility: printed-equation contracts stored by earlier versions carry no consensus evidence and now read as invalid contracts, which refuse approval and keep the artifact gated. Operator action: run remediation again on the affected documents to regenerate those findings. No database migration is involved ([#693](https://github.com/Aelira-AI/aelira-core/issues/693)).
- Equation recognition now accepts LaTeX written with single backslashes. Models commonly write `\frac`, `\approx` or `\int` inside the JSON answer with single backslashes, which JSON either rejects as an invalid escape or turns into a control character (`\f`, `\b`, `\n`, `\r`, `\t`), so the answer was refused and almost no printed equation passed recognition with the documented default local vision model. The printed recognizer, the second reading and the handwritten recognizer and verifier now share one parser. It parses strictly first, and only when that fails, or the parsed LaTeX holds a control character, doubles the unescaped backslashes and parses once more; an answer that already parsed to printable LaTeX is never rewritten, and anything that still holds a control character is rejected. Every check that follows the reading still applies ([#705](https://github.com/Aelira-AI/aelira-core/issues/705)). Thanks to @Vamsi-2581 for an independent fix (#712).
- Generated image descriptions that contain math markup are now refused, never rewritten. A vision model asked to describe an equation usually answered in LaTeX and the description was used as it came, so a screen reader announced backslashes, braces and dollar signs. The generic, chart, validation and classification prompts and the Word, PowerPoint and PDF remediators' prompts now ask for mathematics in plain spoken words. A description that still holds a backslash command, a `$...$`, `$$...$$`, `\(...\)` or `\[...\]` span with mathematics in it, a braced script or a bare script such as `r^2` is refused whole and the image is left for human review with the new manual reason `image_description_math_not_speakable`. Between dollar signs that touch their contents, mathematics is a command, a script, a brace or a bar, a function call, a lone symbol or number, an operator between symbols with or without spaces, or any letter, so `$y = mx + b$`, `$a = 5$`, `$ab$`, `$3.14$` and `$2 × 3$` are refused. A span with a space inside both signs is refused when it holds one of those other than a bare letter, so `$ y = mx + b $` is, while `$$ ab $$` is not, because it cannot be told from the price tier `$$ or $$$`. A dollar sign directly after a letter or digit never opens a span, so currency prefixes such as `US$100` and `A$5` pass, and `echo $HOME$PATH` is still refused as a code-screenshot limit. A description that holds a character that cannot be read as text, such as a NUL, an escape or a direction override, is refused the same way, while line breaks and tabs are kept. Text without such markup is returned unchanged, and prices (`$5 and $10`), price tiers (`$$ or $$$`), units (`($M)`) and file paths are not treated as markup. Known limit: a description of a code screenshot that quotes `print("Hello\n")`, `\d+`, `m^2` or `A_1` reads as markup and is refused, so it goes to manual review. The image alt-text and chart-description routes answer `422` with a message instead of a server error, and the batch and comprehensive-analysis routes carry the message in their response. A classification's recommended alt text is withheld as `null`, never as the empty string that marks a decorative image. Model answers in JSON go through the same tolerant parser as equation readings, so a command written with single backslashes survives to be refused, including a negation such as `\nsubset`, which JSON decodes to a line break and the word "subset" and which would otherwise be announced as its opposite. A swallowed escape is repaired only when the letters complete a listed command name. A real line break before a word that completes one is repaired and refused too, which fails closed. A description taken from an answer in which a swallowed command was repaired is refused whatever the repaired text then looks like, so `categories.\ne.g.` cannot pass as a file path, and a backslash followed by the name of a command is never part of a relative path. Prompt and acceptance revisions changed, so analyses stored under the earlier rules are not replayed. Pending proposals created before this version are not re-checked, and human approval remains the gate for them ([#710](https://github.com/Aelira-AI/aelira-core/issues/710)).
- Equation alt text is now written only for closed spoken forms. The spoken text for a printed or handwritten equation is built by substitution from the recognized LaTeX, which says the words of an equation but not where its parts begin and end, so different equations could share the same words (`x^{n}y` and `x^{ny}`), a command with no spoken form was erased (`\sin x = 0` read "x = 0"), and `\frac13` read "13". An equation is now refused for human review as `image_equation_alt_text_ambiguous` unless every argument of a fraction, binomial, root or script is one number, letter or Greek letter; each fraction, binomial, root or script other than squared and cubed is followed only by the end of the text, a closing parenthesis, a comma or a relation; no script sits on an integral or sum limit; a script written without braces takes one ASCII letter or digit, while a braced script takes one number, letter, Greek letter or infinity (`x^{\alpha}` and `x_{\infty}` are said); no script stands on a closing parenthesis, bracket or bar or on a `\mathrm` group; a `\mathrm` group holds one letter; a closing parenthesis ends an open-ended form only when it closes one opened earlier and what follows it ends the form too; no run of letters spells a word the labels use (`a over b`, `pi`, `times`), and no sequence of runs spells a phrase they use (`a divided by b`), also when a command that only changes how the equation is drawn splits it (`a o\left.ver b`), while a word that occurs only inside a phrase stays an ordinary variable (`ax + by = c` is said); and every command has a spoken form. A binomial coefficient reads "n choose k". The rules are a best-effort set, each added for a case where two different equations read the same, and not a proof that no two accepted equations read alike. Plain grouping, such as `(a + b)c` against `a + bc`, is not protected and relies on the reader announcing brackets; speech generated from the verified MathML ([#698](https://github.com/Aelira-AI/aelira-core/issues/698)) is the planned fix. The check runs on the first and the second reading of a printed equation and on both readings of a handwritten one, and a refused equation stays a manual finding with no Formula written. Generating the spoken text from the verified MathML is planned in [#698](https://github.com/Aelira-AI/aelira-core/issues/698); until then, review the alt text of every equation ([#693](https://github.com/Aelira-AI/aelira-core/issues/693)).
- The v0.9.6 and v0.9.7 notes described printed equation images as "round-trip verified" and each General STEM specialist as having independent verification. For printed equations that was one reading checked by a visual similarity filter, not an equivalence proof, and it could pass a reading one symbol away from the image. Both notes now carry a dated correction, and the [General STEM guide](docs/document-remediation/general-stem.md#what-the-printed-equation-checks-establish) describes what the printed-equation checks establish ([#693](https://github.com/Aelira-AI/aelira-core/issues/693)).
- The API image installs an empty `aelira-xdg-utils-absent` package that provides `xdg-utils`, so `texlive-base`'s dependency is satisfied again and `apt-get install` works in images built from it. v0.9.13 purged `xdg-utils` with dpkg and left `apt-get check` failing with an unmet `texlive-base` dependency. The package ships no files, and `xdg-utils`, `xdg-email` and `xdg-open` stay absent. The final-image package check now allows no unmet dependency, and CI runs `apt-get check` against the built and the published image on both architectures ([#700](https://github.com/Aelira-AI/aelira-core/issues/700)).
- PowerPoint scans now read a picture's alt text from the `descr` attribute on its non-visual properties (`p:nvPicPr/p:cNvPr`), which is where PresentationML keeps it and where remediation writes it. The scanner used to look on the picture element itself, so every picture was reported as missing alt text, any deck with a picture was capped by a critical finding, and the saved-file rescan after remediation could not see the alt text it had just written, so those fixes went back to manual review. Pictures with a real description are no longer reported and affected decks now score higher. Alt text that is only a file name (`photo.JPG`, `C:\pics\photo.png`) or an authoring tool's placeholder (`Picture 3`, `Image 1`, `image001`, `Screenshot`) is reported as missing at the same severity, because it describes nothing; python-pptx writes the file name by default. A real description that merely mentions a file type is not affected. Scans stored earlier keep their results until the document is scanned again ([#713](https://github.com/Aelira-AI/aelira-core/issues/713)).
- A verified printed equation no longer reappears as undescribed after the file is saved. The remediator writes a verified printed equation as a Formula that carries its own alternative text and owns the image's marked content, but the saved-file rescan only credited alternative text held by a Figure. It kept reporting "Image missing alternative text" and the equation candidate, and the fix was demoted as unproven while the Formula stayed in the file. The rescan now credits a Formula that owns exactly one image draw, has a non-empty alternative text and no replacement text, sits under no Figure or replacement ancestor and paints nothing else, inline images included. A Formula never counts as a Figure, so no Figure alternative text is written over it. A Figure whose marked content holds an inline image is likewise no longer treated as the exclusive owner of its draw, so its alternative text is not rewritten ([#694](https://github.com/Aelira-AI/aelira-core/issues/694)).
- An equation image and its alternative-text finding now have one owner. While a verified equation is pending for an image, the generic alt-text pass no longer calls its provider or creates a second owner for that draw. When the equation is proven in the saved file, the finding is promoted to a fix that carries the equation's description, flagged for human review, with the equation fix remaining the single review-gated record. An equation the specialist recognised but could not verify is never described generically, so both findings stay manual, and the image finding reports `image_equation_alt_text_withheld`. An image that already sits inside other marked content, an Artifact included, or whose draw cannot be resolved to exactly one drawing operation, is refused before any equation reading with `image_equation_existing_owner_unsupported` or `image_equation_draw_unresolved`. In an untagged source its alt-text finding is refused too, with `image_in_marked_content` or `image_draw_unresolved`, because a description cannot be bound to such an image. In a tagged source whose Figure already owns the draw, the finding is handled like any other image ([#694](https://github.com/Aelira-AI/aelira-core/issues/694)).
- Remediation now fails closed when review-gated equation content reaches the saved file without a verified review-gated fix. A fix demoted after saving used to leave the Formula and its description in a published file that nothing marked for review, and the job published it with `requires_approval` false. The run now reports failure, closes its output claim and sets the published file aside. The direct and Brightspace PDF routes also store `requires_approval` in the artifact result, computed from the surviving fixes as the queued job does ([#694](https://github.com/Aelira-AI/aelira-core/issues/694)).
- A PDF without a structure tree is no longer withheld whole because an image stays undescribed. For an untagged source, Matterhorn 13-004 reports that figures cannot be checked, and the tagged output reports a count of figures missing alternative text. Saved-file verification treated that as changed evidence, so the file was withheld together with its verified language, title and structure fixes. An image can legitimately stay undescribed when its description cannot be verified, for example an equation whose readings disagree, and every image of an untagged source was undescribed to begin with, so remediation introduced no defect. The change is now accepted only when the saved output's figures account for exactly the source's images, each figure still missing alternative text is a missing-alt finding recorded as manual work in the same result, each described image carries the description of its own verified fix, and the validator's count agrees. Anything else keeps the previous result, such as a source whose structure could not be read rather than being absent, a figure that owns no source image, or a described image whose description no verified fix of that image accounts for. A tagged source whose images sit outside any structure element is not covered: the same failure is new there, not changed, and the file is still withheld when one of those images stays undescribed. An image inside marked content, such as an artifact, together with any other image left undescribed, also still withholds the whole file: this check requires every image the saved file credits to be backed by a verified fix of its own, and an image inside marked content is credited without one. The published result lists the undescribed images as manual work, and review gating for equation content is unchanged ([#714](https://github.com/Aelira-AI/aelira-core/issues/714)).
- Generated image descriptions are now bound to the exact image they describe, or not written. The content tagger paired the Figure written for a description with the next image in order of appearance, so when an earlier image stayed undescribed, such as an equation whose reading was refused, the description of a later image landed on the earlier image's Figure. The saved-file rescan caught the mismatch and moved the fix to manual work, but the whole file was withheld and still held text attached to the wrong image. The Figure now records the rectangle of the one draw it describes, in default user space and taken from the page content, so it holds for rotated pages and crop boxes that do not start at the origin. The tagger binds a Figure to an image only when the two fit each other and nothing else: the Figure overlaps no other image of the page, and no other Figure overlaps the image. A Figure that carries a rectangle is never paired by order, and a Figure without one is written only for a page's single image. A description is refused, with its own manual reason and with no Figure, no HTML alternative and no credited fix, when the image is drawn over another image at nearly the same place, when it sits inside marked content such as an artifact, when its drawing operation cannot be resolved exactly, or when the finding does not identify the image and the page holds others. In a structure generated in this run, a Figure or Formula that carries a description and was bound to no image is removed before saving, wherever it sits in that structure, so such a structure never keeps a description that no image carries. A tagged source keeps its own Figures untouched. The earlier position match could not work: it compared against every image on the page, and the box it compared was in the viewer's coordinates rather than the page's. An untagged document whose first image is undescribed and whose second is described is now saved with the description on the second image and lists the first as manual work ([#715](https://github.com/Aelira-AI/aelira-core/issues/715)).
- PDF remediation for local uploads, Google Drive and Microsoft files now runs printed and handwritten equation recognition, and a PDF that contains an equation image no longer loses AI descriptions for its other images. Since v0.9.7 ([#264](https://github.com/Aelira-AI/aelira-core/pull/264)) these jobs gave the remediator their workspace's provider runtime as the image-description client. Equation recognition accepts only a client bound to the `alt_text` purpose and the runtime carries none, so recognition never ran for them, even with a vision provider configured. When the PDF also held an equation image or a scanned equation region, the remediator dropped that client for the whole document: every other image without alt text went to manual review as "Alt-text AI provider unavailable", whose explanation pointed at the AI configuration although a provider was configured, and the equation finding reported `alt_text_client_unavailable`, which had no public explanation. In v0.9.6 local uploads used a client bound under the LMS AI policy, so recognition ran when that policy allowed alt text, while Google and Microsoft jobs fell back to the global provider manager, which equation recognition refused. These jobs now receive a separate `alt_text`-purpose view of their workspace's own provider runtime whenever the request leaves image descriptions on. The view adds no capability: it calls the same tenant-bound providers and their usage is counted on the same runtime. The queued job, the remediation subprocess, which derives the view again from its own request, and the in-process path all apply it. `generate_alt_text` stays `true` by default for these jobs; a request that sends `false`, which used to be ignored, now keeps image descriptions and equation recognition off and reports image findings as a disabled category. The purpose check moves into equation recognition itself, so a client without the purpose still never reaches it but no longer withholds descriptions of other images. The view names no provider or model of its own, so a recognized equation records the provider and model named in the provider's answer, and a replayed answer still records no model. `alt_text_client_unavailable` and each equation recognition reason now have a public explanation. LMS jobs keep their policy-bound clients. For self-hosted operators, equation images in these PDFs are now sent to the workspace's configured vision provider, as their other images already were. Recognized equations go through the same checks as for LMS jobs, including the blind second reading, and stay behind the review gate: flagged for review and unavailable until a person approves the exact evidence ([#732](https://github.com/Aelira-AI/aelira-core/issues/732)).
- The equation publication gate no longer refuses every PDF that carries a verified equation. The gate refused any Matterhorn result with a failed checkpoint, and remediation never sets the PDF/UA identifier, so checkpoint 06-003 always failed and no artifact with a verified equation could be published by the remediation job, the direct remediation route or Brightspace. In the job the refusal was retryable, so the run's other fixes were discarded and the job retried. The remediator now records the source's failed Matterhorn checkpoints by id and page with multiplicity, and leaves failures whose evidence changed out of that baseline. All three publishers pass the record to the gate, including queued jobs, whose remediator runs in a child process. The gate keeps its integrity checks, so an unavailable, empty, malformed or internally inconsistent result still blocks. Otherwise it blocks only when the output fails more checkpoints than the source did, and with no recorded comparison any failure blocks. A refusal is final for the run and is not retried: the job records a public reason that the candidate was withheld because it would add PDF/UA problems the source did not have and the original is unchanged, and the direct route answers 409 with the same explanation. This was hidden because the saved-file rescan demoted every printed equation fix before publication ([#694](https://github.com/Aelira-AI/aelira-core/issues/694)) ([#697](https://github.com/Aelira-AI/aelira-core/issues/697)).

The verifying fetch helper in `docker/build-lxml-wheel.sh` accepts optional fallback addresses after the destination. A fallback is tried only after every bounded attempt at the previous address failed, gets the same three attempts, and must match the same pinned SHA-256; failure logs identify a fallback by position, not address. zlib falls back to the identical release asset published in the zlib repository, and every other source is unchanged. A broader cache for pinned build-time sources remains open in [#687](https://github.com/Aelira-AI/aelira-core/issues/687) ([#706](https://github.com/Aelira-AI/aelira-core/issues/706)).
