# Aelira v0.9.12

This release covers security hardening, document evidence, reviewed PDF
working files and self-hosted operations. Automated findings and scores do not
establish WCAG conformance.

## Security and reliability

- LaTeX conversion runs every LaTeX tool and pandoc with a minimal environment
  and confined to its own working files and the submitted source, fixing
  [GHSA-53gp-pqcg-h8q4](https://github.com/Aelira-AI/aelira-core/security/advisories/GHSA-53gp-pqcg-h8q4),
  where a submitted document could read files outside its source directory.
  Self-hosted deployments on 0.9.11 or earlier should upgrade.
- Outbound HTTP and browser scan traffic is constrained to validated public
  destinations. Unsupported browser channels leave required checks incomplete.
  Upload paths, OAuth callbacks, diagnostics and API-key storage have tighter
  boundaries. Image descriptions require verified source pixels and a configured
  vision provider.
- CI now requires explicit coverage and skip accounting, PostgreSQL worker and
  race checks, Office preservation, and LaTeX conversion and download evidence.
  These checks complement human review and assistive-technology testing.
- Google and Microsoft integration routes preserve binary download/export and
  durable job identities. Failed account, invitation and notification operations
  retain more accurate stored and user-visible outcomes.
- Production images omit pip's vendored dependencies and the vulnerable Pa11y
  FTP/ZIP downloader chain. Dashboard images install pcre2 and tiff security
  updates. Native scan and publication gates remain required.
- Publication rejects HIGH and CRITICAL vulnerability findings, including
  language-package findings and findings without a fixed version. The only
  exception is an operating-system package finding with no distribution fix
  and a reviewed, expiring disposition that is disclosed: HIGH findings may
  ship as affected, and HIGH or CRITICAL findings may ship as not affected
  with a stated reason the vulnerable code cannot be reached. See
  [known unfixed advisories](#known-unfixed-advisories). Each native image's
  unsuppressed report is retained either way. Embedded native libraries
  require separate assessment; a clean scanner report alone does not
  establish their safety.

## Known unfixed advisories

The API image is built on Debian 13. Its scan reports 64 HIGH advisories and
one CRITICAL advisory in Debian packages that have no Debian fix at
publication time. Each is reviewed and listed, with its packages and
reasoning, in
[known unfixed advisories in v0.9.12](../security/known-unfixed-advisories-0.9.12.md).

- **54 are not affected** in this image. For example, FFmpeg's affected
  decoders and demuxers are excluded by the media allowlists, Tesseract issues
  need model files users cannot supply, and several affect tools or services
  the image does not run.
- **10 are affected and shipped knowingly**: seven in libxml2 and three
  denial-of-service issues in ImageMagick and libtiff, all reachable through
  LaTeX conversion of submitted documents. They will be repaired when fixes
  are available.

Two GnuTLS advisories, CVE-2026-88647 and CVE-2026-88648, are also unfixed;
Debian rates them low and upstream does not treat them as security issues.
Aelira's own HTTPS traffic does not use GnuTLS. All findings remain in the
published scan reports, and the reviews expire on 2027-01-12.

## Document and review changes

- PDF scores keep deterministic findings separate from optional AI review.
  Source/output measurements bind to exact file checksums; unavailable checks
  cannot produce a verified after-score. Repairs retain source-bound evidence,
  and unsafe or unsupported output is withheld.
- A verified improved PDF can be downloaded as a **working file** while manual
  corrections remain. Review shows applied changes, pending decisions and
  remaining work. Download alone does not approve publication. External
  writeback requires separate human approval of the current artifact and a
  fresh check of file identity, accepted fixes and scope.
- Supported PDF structure edits create pending-review candidates. Reviewed
  rebuilding applies accepted edits and excludes rejected edits. PPTX shape
  ordering and LaTeX source/HTML workflows have bounded, format-specific
  support; they do not certify the resulting document's accessibility.
- Supported multiline PDF titles retain their complete source-owned text when
  becoming H1–H6 candidates. Heading checks require nonempty content ownership.
  Scanning and repair share bounded regional reading-order rules, with reopened
  occurrence and graph checks. Mixed content arrays remain immutable; ambiguous
  layouts remain explicit review requirements. Each editor save still requires
  fresh human review before publication.
- Manually edited PDFs retain earlier repair receipts only with saved-byte
  preservation evidence. Conflicting heading edits, unsupported preservation
  scopes and historical copied receipts block approval; candidates remain
  downloadable. Previous job scores describe the earlier output.
- Unknown remediation confidence remains unknown rather than becoming zero or
  an invented high score. Numeric batch approval cannot accept an unknown
  value. Historical generic AI scores may require renewed review after the
  migration below.

feature limits and evidence.

## Operator action required

This release adds two Alembic revisions after v0.9.11:
`20260917_unknown_confidence` (after `20260905_visual_analysis`) and
`20260928_pdf_edit_pub` (the single current head). This is a database migration.

1. Before deploying, pause new intake and review/remediation writers. Drain
   active worker jobs, then stop the API and worker. Take a **coordinated**
   backup of PostgreSQL, uploads, managed remediation/report artifacts, and
   matching private configuration and encryption keys. Verify the restore path
   in separate storage. Include any separately configured artifact directories.
2. Read the [historical confidence correction](../document-remediation/confidence.md#historical-correction),
   inventory affected records with its read-only query, and plan renewed review
   of affected pending fixes and unwritten approved artifacts. The migration
   preserves audit history but may revoke those approvals. It does not undo
   output already written to an external provider.
3. Pull matching v0.9.12 API and dashboard images, or build both from the same
   release revision. Run `alembic upgrade head` explicitly using the new API
   image and confirm success and head `20260928_pdf_edit_pub` before accepting
   traffic. Deploy API, worker and dashboard from that same release; API and
   worker share one image. Confirm API readiness, worker readiness and queue
   progress before reopening intake. Follow the
   [self-hosted upgrade procedure](../deployment/self-hosting.md#upgrade-procedure).
4. Recheck affected review decisions and the exact saved output before approving
   publication. A working PDF with manual findings remains unfinished. Validate
   representative files and provider paths for your deployment.

Do not roll back only an application image or one service. The confidence
migration permits no downgrade while unknown scores remain; older images may
not support nullable confidence. For a return to v0.9.11, quiesce writers and
restore the **matching pre-upgrade database, uploads, artifacts, configuration
and keys together**, then start its matched API, worker and dashboard. A restore
loses post-backup local activity. Reconcile any external writebacks separately.
See the [recovery rehearsal](../deployment/upgrade-recovery-rehearsal.md).

Existing v0.9.11 and earlier operator requirements still apply. Production
branding changes may require matching backend and dashboard settings and a
dashboard rebuild; see [branding](../../BRANDING.md).

Production API images no longer include pip. Rebuild from reviewed requirements
to add or change Python dependencies; the development image retains its
installer. The [locked Pa11y runtime](../../pa11y-runtime/README.md) uses the
image's installed Chromium rather than downloading a browser.

## Publication integrity

Publication remains gated on a signed annotated tag with a GitHub-verified
signature, a successful `ci.yml` **push** run for the exact tagged commit on
the default branch, and the protected `release` environment. Only
`.github/workflows/release.yml` publishes this release body, consumed verbatim.
The workflow builds native `linux/amd64` and `linux/arm64` API/dashboard
images, verifies signed image provenance and signatures, publishes the CLI
through npm trusted publishing, and requires a seven-file SBOM bundle (three
dependency CycloneDX files and four image SPDX files). These are publication
requirements. Check the workflow result and published artifacts before upgrading.
