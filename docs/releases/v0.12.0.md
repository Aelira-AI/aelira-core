# Aelira v0.12.0

This release rewrites how uploads rated high risk are handled. A PDF or a
Word, Excel or PowerPoint file that carries macros or other active content is
now rebuilt without it and checked again, and stored and scanned in that form;
a file that cannot be rebuilt that way is refused with the reasons. It also
makes the validator's macro check run, stops it treating ordinary phrases as
threats, and fixes Canvas error handling, PDF heading and reading-order
findings, PDF refusal messages, alert emails and dashboard text. It adds no
database migration. Automated findings and scores do not establish WCAG
conformance.

It is a minor release because uploads rated high are now refused when they
cannot be rebuilt, and the validator rates more kinds of active content as
high, as described under [Versioning](../../README.md#versioning) and under
[Operator action required](#operator-action-required). Two fixes also change
what the API returns without removing or renaming anything: the Canvas course,
file and folder routes answer a Canvas failure with 502, 503, 403 or the
existing 409 instead of an unhandled 500, and the session check adds a
read-only `has_api_keys` flag. Deployments upgrading from 0.10.0 or earlier
must also follow the [v0.11.0 operator
steps](v0.11.0.md#operator-action-required).

## Upload security

Self-hosted deployments that accept document uploads should upgrade.

- **Rebuilt uploads**
  ([#863](https://github.com/Aelira-AI/aelira-core/issues/863),
  [#871](https://github.com/Aelira-AI/aelira-core/issues/871)). When the
  validator rated a file high, the upload routes stored the original upload
  but queued the scan with the hash of a rebuilt copy, so the scan failed with
  `local_scan_input_hash_mismatch` and the stored file kept the content the
  rebuild was meant to remove. The rebuild itself removed Office parts by file
  name, left the relationships, content types and document elements that named
  them, and rewrote hyperlinks as internal links, so a rebuilt Office file
  could not be read; when it failed it returned the original bytes; and every
  such upload was recorded as sanitised. The PDF rebuild deleted byte ranges
  with regular expressions. Now an Office file is rebuilt from its content
  types and relationships: VBA projects and their data, macro customisations,
  ActiveX controls, Excel 4 macro sheets, embedded and linked OLE objects and
  packages, custom ribbons and attached templates are removed with everything
  that names them, external frames and subdocuments are removed, and
  hyperlinks, text, images and remaining sheets are kept. A PDF is rebuilt with
  pikepdf without its scripts, automatic actions, XFA forms and active actions,
  keeping links, destinations and text. The rebuilt file is validated again,
  and only then stored, scanned and recorded as sanitised.
- **Refusals**
  ([#863](https://github.com/Aelira-AI/aelira-core/issues/863)). A file whose
  rebuild fails or is still rated high, a legacy `.doc`, `.xls` or `.ppt` file,
  and an Office file in another format are refused with the findings and
  recorded as blocked. Code files (HTML, CSS, JavaScript and code archives)
  have no rebuild; they are processed as uploaded, as before, and are no longer
  recorded as sanitised.
- **Macro check**
  ([#860](https://github.com/Aelira-AI/aelira-core/issues/860),
  [#872](https://github.com/Aelira-AI/aelira-core/issues/872)). The macro
  check on `.docx`, `.xlsx` and `.pptx` files never ran: it imported a function
  that oletools 0.60.2 does not provide, so a file carrying a VBA project was
  neither rated high nor rebuilt. It now uses the oletools parser. A macro is
  rated high and the file is rebuilt without it. A macro that calls Shell,
  CreateObject or Environ, with or without parentheses, or that names
  WScript.Shell, PowerShell, cmd.exe or a download or registry function, is
  rated critical and refused. A VBA project the parser cannot read is also
  rated high.
- **More active content rated high**
  ([#863](https://github.com/Aelira-AI/aelira-core/issues/863)). The validator
  now rates as high an Excel 4 (XLM) macro sheet, an attached template, frame,
  subdocument or OLE object loaded from outside the file, and an Office package
  whose content types or relationships cannot be parsed. It matches PDF
  keywords as whole names with `#hh` escapes decoded, so `/J#61vaScript` is
  found and `/JSomething` is no longer counted as `/JS`.
- **Phrase screening**
  ([#856](https://github.com/Aelira-AI/aelira-core/issues/856)). The
  validator rated an Office file as a high threat whenever its text contained
  an ordinary phrase such as "act as", "user:", "system:" or "pretend to be",
  and the upload then failed to scan. A document that said "the valve can act
  as a buffer" could not be scanned at all. The validator no longer screens
  document text for phrases. An upload that is rebuilt or allowed through is
  no longer recorded as blocked.

## Other fixes

- **Canvas errors**
  ([#736](https://github.com/Aelira-AI/aelira-core/issues/736)). When Canvas
  answered a course, file or folder listing with an error or could not be
  reached, users saw a generic server error, including when Canvas was not
  ready right after the OAuth callback. The routes now return 502 for a Canvas
  server error, 503 when Canvas rate-limits, times out or cannot be reached,
  the existing 409 "reconnect your Canvas account" response when Canvas
  rejects the token, and 403 with a fixed message when Canvas denies the
  request. The messages are fixed text; the Canvas response body, URL, token
  and exception text are never returned.
- **PDF refusal reasons**
  ([#804](https://github.com/Aelira-AI/aelira-core/issues/804)). When the PDF
  remediator refused a file because its text encoding or text scope could not
  be verified, the result page showed "legacy_unverified" with no guidance. It
  now shows the existing message about exporting a new PDF or repairing the
  font mappings. The job still fails and no output is published.
- **PDF first heading**
  ([#830](https://github.com/Aelira-AI/aelira-core/issues/830)). A PDF whose
  first heading was an H1 could get an unrepairable "Document should start
  with H1 heading" finding when the heading scan stopped at a later heading,
  for example an empty one. A first heading confirmed as an H1 now clears that
  finding.
- **PDF reading order**
  ([#831](https://github.com/Aelira-AI/aelira-core/issues/831),
  [#832](https://github.com/Aelira-AI/aelira-core/issues/832)). The
  reading-order check re-read up to 100 pages for every page it analysed, so
  long documents with sparse page numbers took far longer than needed; each
  page is now read once and the findings are unchanged. Its review
  requirements and recommendations showed internal codes such as
  `reading_order_region_work_limit` and raw exception text; they now use plain
  sentences.
- **Alert emails**
  ([#816](https://github.com/Aelira-AI/aelira-core/issues/816)). Every
  scan-complete alert failed and the weekly summary job raised, because both
  read fields the scan record does not have. They now read the score and
  findings from the scan result and show the email body as text instead of
  escaped markup. Their links, and those in the remediation result emails, now
  open the scan page at `/scan/{id}` under the configured dashboard URL; they
  pointed at `dashboard.example.com`, a relative link or `/scans/{id}`, which
  the dashboard does not serve.
- **Dashboard text**
  ([#859](https://github.com/Aelira-AI/aelira-core/issues/859)). Badges read
  "WCAG WCAG 1.3.1", counts read "1 issues", the review header showed the scan
  id, the approved working file was named `source_remediated.docx`, Word
  documents showed the PDF-only Matterhorn Protocol bar, every account saw the
  retired API key banner, raw values such as `rule_based` and `font_size`
  were shown as labels, and every Office finding on the Issues page was
  categorised "Other". Each now shows readable text, the working file is named
  after the upload, and the API key banner appears only to an account that
  owns or once owned API keys.

See the [changelog](../../CHANGELOG.md) for the full entries.

## Changes and limits

- Office uploads whose text contains phrases such as "act as" keep their
  embedded objects. Security records written before this release are not
  rewritten.
- A PDF with JavaScript, and a Word, Excel or PowerPoint file with macros,
  ActiveX controls, embedded OLE objects or an attached template, is rebuilt
  and scanned, so its results and working file come from the rebuilt copy
  without that content. Embedded objects such as OLE equations are removed
  from these files and their preview images are kept. Before, such a PDF
  failed to scan, and such an Office file was scanned with its macros or
  failed to scan.
- Uploads that the validator rates high and that cannot be rebuilt, such as a
  file with a damaged package structure or a legacy `.doc`, are refused with
  the findings instead of failing later with an internal code.
- Accounts with scan-complete alerts turned on start receiving those emails,
  which previously failed with only a warning in the log. A scan with no
  result, score or recorded findings sends no scan-complete email, and the
  weekly summary shows "Not available" for it instead of a zero.
- A strict scan now fails as incomplete when the PDF heading scan stops on a
  size or work limit or an unexpected error, instead of returning a score.

## Known limits and open security items

These findings were disclosed in the [v0.10.0
notes](v0.10.0.md#known-limits-and-open-security-items), where each is
described, and are unchanged in this release. Disclosure is not a gate result.

- libX11 CVE-2026-94283, CVE-2026-94284 and CVE-2026-94285 (MEDIUM) are fixed
  in the rebuilt `libx11`, but the image scanner still reports them
  ([#605](https://github.com/Aelira-AI/aelira-core/issues/605),
  [#739](https://github.com/Aelira-AI/aelira-core/issues/739)).
- PDFium CVE-2026-113022 in `pypdfium2` 5.14.0 has no fixed release
  ([#747](https://github.com/Aelira-AI/aelira-core/issues/747)).
- MuPDF CVE-2026-112036 is not fixed by PyMuPDF 2.0, and the FreeType and MuJS
  versions in its MuPDF build are unverified
  ([#755](https://github.com/Aelira-AI/aelira-core/issues/755)).
- ImageMagick CVE-2026-106576 is affected, a denial of service bounded by the
  tool timeout ([#750](https://github.com/Aelira-AI/aelira-core/issues/750)).
- The Pa11y runtime still forces zod to 4.6.7 until it moves to Pa11y 10
  ([#786](https://github.com/Aelira-AI/aelira-core/issues/786)).
- The development and quickstart images keep pip 26.2.2, whose wheel vendors
  `setuptools` 70.3.0
  ([#578](https://github.com/Aelira-AI/aelira-core/issues/578)).
- A web scan still fails as a whole when a page loads a required resource
  through an HTTP redirect
  ([#800](https://github.com/Aelira-AI/aelira-core/issues/800)).
- The scanner's browser is still the pinned Chrome for Testing 156.0.8078.47.
  A later Chrome stable release is not included.
- The other disclosures in the
  [advisory record](../security/known-unfixed-advisories-0.9.12.md) still
  apply, and the broader libxml2, embedded-library and database-driver
  assessments remain open
  ([#579](https://github.com/Aelira-AI/aelira-core/issues/579),
  [#583](https://github.com/Aelira-AI/aelira-core/issues/583),
  [#588](https://github.com/Aelira-AI/aelira-core/issues/588)).
- An Office file with more than 1,000 parts is rated high as a possible
  archive attack, and since a rebuild cannot change that it is refused. A very
  large deck or document can reach that count
  ([#874](https://github.com/Aelira-AI/aelira-core/issues/874)).
- Code files rated high (HTML, CSS, JavaScript and code archives) have no
  rebuild and are processed as uploaded, in the scanner's browser.
- When the PDF heading scan stops on an empty or unbound heading or an invalid
  parent relation, the reviewer is not told why
  ([#866](https://github.com/Aelira-AI/aelira-core/issues/866)).
- PDF findings record no category, so the Issues page still shows them as
  "Other" ([#873](https://github.com/Aelira-AI/aelira-core/issues/873)).
- Delimiters and the data notice limit, but cannot rule out, a document
  steering what a model writes. Review AI-generated text before publishing
  remediated content.

## Release evidence and open gates

The release workflow builds and verifies the API and dashboard images from the
signed `v0.12.0` tag, and its run and published artifacts are the evidence for
this release. This page does not restate their results, and it does not claim
an upgrade rehearsal from v0.11.1. The same `linux/amd64` and `linux/arm64`
gates apply as for earlier releases.

The changes are covered by unit and integration tests. The upload rebuild is
tested with Word, Excel and PowerPoint files made by python-docx, openpyxl and
python-pptx and given active content the way Office stores it, each opened
again by the same library after the rebuild, and with PDFs that carry scripts.
The macro check is tested with generated Office files that carry a real VBA
project, and the Canvas error handling with a stubbed Canvas client. This page
does not claim a test with files saved by Microsoft Office itself or against a
live Canvas instance.

Final artifact, platform, packed CLI and provider acceptance
([#377](https://github.com/Aelira-AI/aelira-core/issues/377)), expanded user
journeys ([#375](https://github.com/Aelira-AI/aelira-core/issues/375)),
dashboard assistive-technology work
([#376](https://github.com/Aelira-AI/aelira-core/issues/376)) and PowerPoint
acceptance ([#373](https://github.com/Aelira-AI/aelira-core/issues/373)) remain
open.

## Operator action required

Uploads behave differently in this release. A PDF or Office upload rated high
risk is rebuilt without its macros, scripts, ActiveX controls, embedded objects
and external templates and then scanned, so its results and working file come
from the rebuilt copy. An upload that cannot be rebuilt is refused with the
reasons, and the security record says it was blocked. Tell the people who
upload documents, and check the security records of refused uploads if they
ask why a file was turned away.

This release adds no database migration. The single Alembic head stays
`20261028_webhook_secret`, after `20261020_media_captions`,
`20261018_media_truth`, `20261017_canvas_scope` and the v0.9.12 head
`20260928_pdf_edit_pub`.

1. Before deploying, pause new intake and review/remediation writers. Drain
   active jobs, stop API and worker, and take a verified **coordinated backup**
   of PostgreSQL, uploads, managed report/remediation artifacts, and matching
   private configuration and encryption keys. Include separately configured
   artifact storage and verify a restore path.
2. Pull the exact approved `linux/amd64` or `linux/arm64` API and dashboard
   images, or build both from the **same release** revision. Run
   `alembic upgrade head` explicitly with the matching API image, confirm the
   head is still `20261028_webhook_secret`, then deploy API, worker and
   dashboard together. Check API and worker readiness and queue progress before
   reopening intake.
3. Deployments upgrading from 0.10.0 or earlier must first complete the
   [v0.11.0 operator steps](v0.11.0.md#operator-action-required), including
   creating Microsoft webhook subscriptions again.
4. Recheck source identity, remaining findings and the exact saved output. A
   working file requires separate human approval before publication or external
   writebacks. Unsafe or unsupported output is withheld.

A rollback requires quiescing writers and restoring the matching
**pre-upgrade database**, uploads, artifacts, configuration and encryption keys
with the previous API, worker and dashboard images. Local activity after that
backup is lost; reconcile external writebacks separately. Follow the
[upgrade and recovery procedure](../deployment/upgrade-recovery-rehearsal.md)
and the [v0.9.12 operator notice](v0.9.12.md#operator-action-required).

## Publication integrity

The [release workflow](../RELEASE_INTEGRITY.md) requires this checked-in body
to be consumed verbatim. Publication requires a **signed annotated tag** with a
**GitHub-verified** signature, a successful `ci.yml` push run for the exact
tagged commit on the default branch, and approval through the protected `release` environment.
It must build and verify native `linux/amd64` and
`linux/arm64` API/dashboard images, signed image provenance and signatures,
the CLI through npm trusted publishing, and a seven-file SBOM bundle (three
dependency CycloneDX files and four image SPDX files). The release safety
scan, reviewed vulnerability dispositions and all exact-artifact gates still
apply. Check the workflow result and published artifacts before upgrading.
