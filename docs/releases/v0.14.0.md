# Aelira v0.14.0

This minor release pairs one scan behaviour fix with broad artefact hygiene.
The fix scores tagged PDFs that associate annotations through OBJR structure
children — hyperlinks with alternative text, form widgets, Word exports —
which previously failed the reading-order completeness check and were not
scored ([#1004](https://github.com/Aelira-AI/aelira-core/issues/1004)).
Around it, the release advances the pinned dependencies the published
artefacts run on, retires the custom `zlib1g` rebuild in favour of the
Debian security update that now carries the same fix, records reviewed
dispositions for advisories with no upstream fix, closes the PDFium
CVE-2026-113022 gap through `pypdfium2` 5.15.2, and adds the release-preflight
tooling that keeps merged dependency PRs and the changelog aligned. The
release adds no database migrations. It is a minor release under
[Versioning](../../README.md#versioning) because the scan behaviour changes
and major dependency lines inside the shipped artefacts moved — `pypdf` 7 on
the PDF reading path, `webauthn` 3 on the passkey path, `python-dateutil` 4,
`cachetools` 8. Automated findings and scores do not establish WCAG
conformance.

Deployments upgrading from 0.11.1 or earlier must also follow the [v0.12.0
operator steps](v0.12.0.md#operator-action-required), whose upload behaviour
changes still apply, and deployments upgrading from 0.10.0 or earlier the
[v0.11.0 operator steps](v0.11.0.md#operator-action-required).

## Fixes

- Tagged PDFs whose structure tree associates annotations through OBJR
  children (ISO 32000-1 14.12.3.4) are now scored. An OBJR whose `/Obj`
  resolves to a dictionary and which carries no page-stream marked content is
  skipped with the order unchanged; OBJRs whose `/K` hides page-stream content
  or whose `/Obj` is missing or not a dictionary still fail closed.
  Remediation still refuses OBJR documents
  ([#1004](https://github.com/Aelira-AI/aelira-core/issues/1004),
  [#1005](https://github.com/Aelira-AI/aelira-core/pull/1005)).

## Security

- The custom `zlib1g` rebuild retired: Debian's `1:1.3.dfsg+really1.3.1-1+deb13u1`
  security update carries the same `gz_write` fix plus a `crc32_combine`
  guard, so both images install the distribution package directly and the
  patch that collided with Debian's own retires with the recipe
  ([#957](https://github.com/Aelira-AI/aelira-core/issues/957)).
- The dashboard image upgrades `musl` and `musl-utils` to 1.2.6-r3 through the
  production-stage apk security allowlist, clearing the HIGH CVE-2026-107891
  findings the Alpine base predates
  ([#960](https://github.com/Aelira-AI/aelira-core/issues/960)).
- The CLI dependency tree no longer resolves the vulnerable `minimatch` 10.x
  releases: a blanket `minimatch` 11 override became possible once
  `eslint-plugin-import-x` 4.18.0 dropped the `makeRe` import that had made it
  crash config load; every resolved copy is now 11.0.1 or newer
  ([#943](https://github.com/Aelira-AI/aelira-core/issues/943)).
- Fourteen unfixed upstream MIT Kerberos advisories carry reviewed
  not-affected dispositions across two batches: the vulnerable code sits in
  KDC, kadmind and RPCSEC_GSS server paths the API image never executes
  ([#1000](https://github.com/Aelira-AI/aelira-core/issues/1000),
  [#1008](https://github.com/Aelira-AI/aelira-core/issues/1008)).
- The dashboard image carries a rebuilt libxslt revision 4, and the native
  lxml acceptance parser now accepts apt's pending-action selection groups,
  ending the both-arch false refusals
  ([#1011](https://github.com/Aelira-AI/aelira-core/pull/1011)).
- `pypdfium2` 5.15.2 bundles PDFium 159.0.8149.0, closing the bundled-PDFium
  gap for CVE-2026-113022
  ([#747](https://github.com/Aelira-AI/aelira-core/issues/747)).

## Known limits and open security items

These findings were disclosed in the [v0.13.0
notes](v0.13.0.md#known-limits-and-open-security-items), where each is
described, and remain open unless updated here. Disclosure is not a gate
result.

- MuPDF CVE-2026-112036 is not fixed by PyMuPDF 2.0, and the FreeType and MuJS
  versions in its MuPDF build are unverified; `PyMuPDF` stays held at 2.0 for
  that review ([#755](https://github.com/Aelira-AI/aelira-core/issues/755)).
- ImageMagick CVE-2026-116149 remains unfixed in Debian `trixie-security`; the
  packed-pixel heap-buffer-overflow path is not exercised by PDF page
  rasterisation and stays bounded by the ImageMagick policy and tool timeout
  ([#750](https://github.com/Aelira-AI/aelira-core/issues/750)).
- The Pa11y runtime still forces zod to 4.6.7 until it moves to Pa11y 10
  ([#786](https://github.com/Aelira-AI/aelira-core/issues/786)).
- The development and quickstart images keep pip 26.2.2, whose wheel vendors
  `setuptools` 70.3.0.
- A web scan still fails as a whole when a page loads a required resource
  through an HTTP redirect
  ([#800](https://github.com/Aelira-AI/aelira-core/issues/800)).
- The scanner's browser is still the pinned Chrome for Testing 156.0.8078.47.
  A later Chrome stable release is not included.
- The other disclosures in the
  [advisory record](../security/known-unfixed-advisories-0.9.12.md) still
  apply, and the broader embedded-library assessment remains open
  ([#583](https://github.com/Aelira-AI/aelira-core/issues/583)).
- An Office file with more than 10,000 parts (or another zip archive with more
  than 1,000 entries) is rated high as a possible archive attack, and since a
  rebuild cannot change that it is refused
  ([#874](https://github.com/Aelira-AI/aelira-core/issues/874)).
- Delimiters and the data notice limit, but cannot rule out, a document
  steering what a model writes. Review AI-generated text before publishing
  remediated content.

## Release evidence and open gates

The release workflow builds and verifies the API and dashboard images from the
signed `v0.14.0` tag, and its run and published artifacts are the evidence for
this release. This page does not restate their results, and it does not claim
an upgrade rehearsal from v0.13.0. The application change is confined to the
scan reading-order gate described under Fixes, covered by its regression tests;
everything else is dependency and image content, and each batch cleared its
own contract, consumer-fixture and image gates as a merged pull request. The
same `linux/amd64` and `linux/arm64` gates apply as for earlier releases,

## Operator action required

This release adds **no database migrations**; the Alembic head is unchanged
from v0.13.0 (`20261031_totp_mfa`).

1. Before deploying, pause new intake and review/remediation writers. Drain
   active jobs, stop API and worker, and take a verified
   **coordinated backup** of PostgreSQL, uploads, managed
   report/remediation artifacts, and matching private
   configuration and encryption keys. Include separately configured
   artifact storage and verify a restore path.
2. Pull the exact approved `linux/amd64` or `linux/arm64` API and dashboard
   images, or build both from the **same release** revision. Deploy API,
   worker and dashboard together; no schema step is required. Check API and
   worker readiness and queue progress before reopening intake.
3. Because `pypdf` and `webauthn` crossed majors inside the artefacts, smoke
   test one PDF scan through the education processor and one passkey
   sign-in on a staging account before reopening intake to production
   traffic. To exercise the OBJR scan fix, scan a tagged PDF that carries
   hyperlink annotations and confirm it scores instead of returning the
   incomplete-scan message.
4. Recheck source identity, remaining findings and the exact saved output. A
   working file requires separate human approval before publication or
   external writebacks. Unsafe or unsupported output is withheld.

A rollback requires quiescing writers and restoring the matching
**pre-upgrade database**, uploads, artifacts, configuration and encryption
keys with the previous API, worker and dashboard images. Local activity after
that backup is lost; reconcile external writebacks separately. Follow the
[upgrade and recovery procedure](../deployment/upgrade-recovery-rehearsal.md)
and the [v0.9.12 operator notice](v0.9.12.md#operator-action-required).

## Publication integrity

The [release workflow](../RELEASE_INTEGRITY.md) requires this checked-in body
to be consumed verbatim. Publication requires a **signed annotated tag** with a
**GitHub-verified** signature, a successful `ci.yml` push run for the exact
tagged commit on the default branch, and approval through the protected `release` environment.
It must build and verify native `linux/amd64` and
`linux/arm64` API/dashboard images, signed image provenance and signatures,
the CLI through npm trusted publishing, and a seven-file SBOM bundle (three
dependency CycloneDX files and four image SPDX files). The release safety
scan, reviewed vulnerability dispositions and all exact-artifact gates still
apply. Check the workflow result and published artifacts before upgrading.
