## Completed on main after v0.9.5

The following changes are present on `main` after the immutable v0.9.5 tag. Their presence on `main` does not by itself put them in an immutable release or a deployment.

### Release publication integrity

- [PR #163 — fix(release): make SBOM downloads rerun-safe](https://github.com/Aelira-AI/aelira-core/pull/163) (`c413aac6b698e68dd96ae2f4b45c874cebd6e48d`): release reruns select the intended SBOM/publication artifacts without consuming stale or ambiguous artifacts from an earlier attempt. Attempt-agnostic download patterns retain the exact seven-file SBOM verification and existing release gates.

### Public remediation documentation

- [PR #164 — docs: add public document remediation guides](https://github.com/Aelira-AI/aelira-core/pull/164) (`de1ea052c9b6e42572577599bbc08403540c5323`): adds canonical public PDF, Office, and LaTeX remediation documentation. The guides document format boundaries, dependencies, entry points, managed artifacts, preservation limits, evidence, and human review while keeping documents, LMS, web, and media as equal product pillars.

### PDF remediation output

- [PR #165 — fix(pdf): preserve OCR layer in remediated output](https://github.com/Aelira-AI/aelira-core/pull/165) (`4892ac9eac1cc2713d16468c99e38637d46f65fe`):
  - OCR-generated searchable text survives into the delivered PDF, while original PDFs remain immutable.
  - OCR suitability and output text are assessed per page.
  - Signature, XFA, language, partial-text, OCR-refusal, and indeterminate cases fail closed.
  - Failed candidate generation or validation does not replace a prior valid output.
- [PR #166 — fix(pdf): sanitize accessible HTML output](https://github.com/Aelira-AI/aelira-core/pull/166) (`46be8e4e0faa59ff824281b70dc3749e24f73a34`):
  - PDF-derived titles and alt text are normalized and escaped.
  - PyMuPDF fragments are rebuilt through a passive allowlist.
  - Active content, event handlers, styles, unsafe URLs, comments, and malformed structures are removed or normalized.
  - Embedded images accept only validated PNG/JPEG data URLs under byte, dimension, and pixel bounds.
  - Pillow verifies, independently reopens, and fully loads pixels; exact-EOF terminal markers are required.
  - Trailing data, polyglots, spoofing, corruption, decompression risks, and synthetic relative requests are rejected.
- [PR #168 — fix(pdf): bind remediation output publication](https://github.com/Aelira-AI/aelira-core/pull/168) (`e996e082db80058fdd55e3bcab4b9d5617e89ce2`):
  - PDF and optional HTML candidates use retained directory descriptors.
  - The validated PDF is snapshotted into a private, unlinked output claim before final pathname exposure; internal verification consumes that claim rather than reopening `output_file`.
  - Direct, queued, and Brightspace flows publish the exact claimed stream.
  - Size, SHA-256, MIME type, scan type, and filename are recomputed.
  - Claims are read-only, non-inheritable, non-serialized, and single-owner; copy, deep-copy, and pickle are rejected while a claim is live.
  - Cancellation, ownership-fence, and completion-commit failures abort only the exact DB-first staging publication identified by artifact ID and private publication token.
  - Cleanup failures remain explicit and recoverable.
  - Path compatibility remains for library consumers and non-PDF formats. Managed PDF publication is descriptor-bound and Unix/macOS/Linux-specific.

## Planned for v0.9.6

### Verified image-equation to MathML remediation for PDFs

[Issue #167](https://github.com/Aelira-AI/aelira-core/issues/167) is planned, not implemented. The intended initial corpus is printed, standalone, single-equation images addressable by xref/bbox and supported by `latex2mathml`.

The planned contract requires:

- exact equation-image localization by page, xref, occurrence identity, image index, and bbox;
- scanner/category/API normalization so the image issue reaches `MathFixer` intact;
- bounded source image validation;
- authorized, purpose-bound vision using the existing policy boundary;
- strict image-to-LaTeX response parsing;
- conversion through `latex2mathml`;
- deterministic source-versus-rendered round-trip verification before mutation;
- fail-closed handling for parse, provider, conversion, renderer, comparison, policy, or audit failure;
- no `<mtext>` fallback for image-derived formulas;
- content-associated `/Formula`, `/Alt`, and embedded MathML `/AF`, rather than bbox-only placement;
- parity with text-layer LaTeX output;
- `ai_vision` confidence capped at 0.55;
- `needs_review=True` unconditionally;
- explicit human acceptance before artifact approval;
- configured hosted and local-provider support;
- no-provider degradation to detection-plus-manual; and
- preservation of direct, queued, and Brightspace exact-byte publication.

Full-page region discovery, multi-equation screenshots, vector-only regions without localization, handwriting, chemical structures, commutative diagrams, and mixed STEM visuals remain outside this initial corpus. They are deferred rather than permanently excluded.

## Future work planned for v0.9.7

General STEM visual semantics is future work, not part of v0.9.6 and not implemented or available. Its proposed pipeline is bounded region discovery, candidate classification, specialist recognition, semantic representation, specialist verification, PDF content association, and mandatory human review.

Candidate types are:

- `printed_equation`;
- `handwritten_equation`;
- `multi_equation_region`;
- `vector_equation`;
- `chemical_formula`;
- `chemical_structure`;
- `commutative_diagram`; and
- `unknown_math_visual`.

The future workstreams cover full-page scanned documents, multi-equation screenshots, vector equations, handwritten math, chemical formulas, chemical structures, commutative diagrams, and mixed STEM visuals. Each specialist must define its supported corpus, semantic output type, deterministic verifier, confidence ceiling, mandatory-review contract, and fail-closed rules.
