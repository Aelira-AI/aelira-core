# Aelira v0.11.0

This release fixes four security issues, one of them high severity, in the
Microsoft 365 integration and in the dashboard's LMS review pages. It adds one
database migration, and Microsoft webhook subscriptions created before this
release must be created again. Automated findings and scores do not establish
WCAG conformance.

It is a minor release because it changes API behaviour and adds a database
migration, as described under [Versioning](../../README.md#versioning). The
changes that need action are listed under Operator action required.

## Security fixes

Self-hosted deployments on 0.10.0 or earlier that connect Microsoft 365 should
upgrade. Deployments that do not use the Microsoft 365 integration are affected
only by the last item.

- **OneDrive paging links, high**
  ([GHSA-cxmg-mrg8-j7r6](https://github.com/Aelira-AI/aelira-core/security/advisories/GHSA-cxmg-mrg8-j7r6)).
  `GET /microsoft/onedrive/files` used its `page_token` parameter unchanged as
  the URL of the next request, and that request carried the department's
  Microsoft Graph access token, so an authenticated user of the department
  could have the token sent to whatever URL the page token named. OneDrive
  paging and delta links, including that page token, are now followed only
  when they are https URLs on `graph.microsoft.com` under `/v1.0/`, with no
  other port, no user information, no fragment and no dot segments. Anything
  else is refused before a request is sent, and the route answers 400
  `Invalid page token`. Deployments with no connected Microsoft 365 account had
  no token to expose.
- **Graph request paths, low**
  ([GHSA-cpcw-3584-j8q4](https://github.com/Aelira-AI/aelira-core/security/advisories/GHSA-cpcw-3584-j8q4)).
  Graph request paths were built from item, folder, drive, site and
  subscription IDs, SharePoint folder paths and upload file names as given, so
  an ID or path containing `/`, `..`, `?`, `#` or `%` changed which Graph
  resource was requested. The requests still used the connected Microsoft
  account and stayed within its permissions. An ID must now be a single Graph
  ID segment, folder paths refuse dot segments and control characters, and
  every path segment, file name and search term is percent-encoded. The
  Microsoft routes answer a refused reference with 400
  `Invalid Microsoft item reference` before any Graph request.
- **Microsoft webhook notifications, low**
  ([GHSA-5prr-c8m5-63r7](https://github.com/Aelira-AI/aelira-core/security/advisories/GHSA-5prr-c8m5-63r7)).
  Graph subscriptions were created with the department ID as `clientState`,
  and the webhook accepted a notification that carried it with a known
  subscription ID. A department ID is not a secret. An accepted notification
  queues a sync job for the department, so the effect was unwanted sync work.
  Each subscription now gets a random secret, which Graph sends back with every
  notification. The API stores only its SHA-256 hash and compares it in
  constant time, and the notification URL is fixed to the API's own
  `/webhooks/microsoft` route. Existing subscriptions must be created again, as
  described under Operator action required.
- **LMS review pane, low**
  ([GHSA-724p-6r8m-h85x](https://github.com/Aelira-AI/aelira-core/security/advisories/GHSA-724p-6r8m-h85x)).
  The Canvas content diff and Brightspace review pages sanitised the original
  LMS HTML with DOMPurify, then parsed and serialised it a second time to add
  a notice to images with no alt text, so the markup shown was not the markup
  DOMPurify had checked. No working payload is known. The notice is now added
  inside DOMPurify's own pass, and its output is rendered exactly as returned.

## Changes and limits

- `POST /microsoft/subscriptions` no longer requires `notification_url`.
  Notifications always go to `PUBLIC_API_URL` followed by
  `/webhooks/microsoft`, and a request that names any other URL is refused
  with 422.
- A Microsoft sync folder must now be added with its Graph item ID, and
  `POST /integrations/sync-folders` refuses anything else with 422. A sync
  folder already stored with an ID that is not a Graph ID fails its sync as a
  deterministic error that lists the folder, instead of being retried.
- A brief upstream outage while fetching pinned build inputs no longer fails an
  otherwise healthy CI or release build. Every pinned download in the API image
  build goes through one verifier with bounded retries and fallback addresses.
  CI and the release workflow first read those files from a cache keyed by
  their pinned SHA-256, and every cached file passes the same SHA-256 check as
  a download ([#687](https://github.com/Aelira-AI/aelira-core/issues/687)). The
  native LaTeXML jobs build from a cached snapshot input when
  `snapshot.ubuntu.com` refuses all three capture attempts as unavailable. The
  cached input is accepted only against a reviewed lock, every file and the
  signed index chain are authenticated again, and integrity, TLS and other
  refusals never fall back
  ([#840](https://github.com/Aelira-AI/aelira-core/issues/840)).
- Dependency updates: Python runtime packages including FastAPI 0.161.1,
  Starlette 1.9.0, SQLAlchemy 2.1.6, alembic 1.20.1 and certifi 2026.10.23;
  the CLI's @axe-core/playwright 4.14.0, @oclif/core 5.1.9 and
  @oclif/plugin-help 7.0.5
  ([#835](https://github.com/Aelira-AI/aelira-core/issues/835)); and the
  dashboard's react and react-dom 19.3.1 and vite 8.3.5
  ([#825](https://github.com/Aelira-AI/aelira-core/pull/825)).
- ImageMagick CVE-2026-116149, published on 2026-10-25 with no Debian fix, is
  reviewed as not affected, because the converter refuses bzip2-compressed
  input before LaTeXML starts. See the
  [advisory record](../security/known-unfixed-advisories-0.9.12.md#imagemagick-bzip2-advisory-published-on-2026-10-25)
  ([#826](https://github.com/Aelira-AI/aelira-core/issues/826)).
- The [v0.9.13 notes](v0.9.13.md) carry a dated correction of which equation
  path could write alt text into a saved file without review
  ([#810](https://github.com/Aelira-AI/aelira-core/issues/810)).

See the [changelog](../../CHANGELOG.md) for the full dependency list and issue
links.

## Operator action required

This release adds one database migration, `20261028_webhook_secret`. It becomes
the single Alembic head, after `20261020_media_captions`,
`20261018_media_truth`, `20261017_canvas_scope` and the v0.9.12 head
`20260928_pdf_edit_pub`. It adds a nullable `client_state_hash` column to
`cloud_webhook_subscriptions` with no backfill, and does nothing if the column
already exists. Its downgrade drops nothing: earlier releases ignore the
column, and hashes stored by this release survive a downgrade and a later
upgrade.

1. Before deploying, record every Microsoft webhook subscription. For each
   department that connects Microsoft 365, call `GET /microsoft/subscriptions`
   with that department's API key and note the `resource` of each entry.
2. Then pause new intake and review/remediation writers. Drain active jobs,
   stop API and worker, and take a verified **coordinated backup** of
   PostgreSQL, uploads, managed report/remediation artifacts, and matching
   private configuration and encryption keys. Include separately configured
   artifact storage and verify a restore path.
3. Pull the exact approved `linux/amd64` or `linux/arm64` API and dashboard
   images, or build both from the **same release** revision. Run
   `alembic upgrade head` explicitly with the matching API image, confirm the
   head is `20261028_webhook_secret`, then deploy API, worker and dashboard
   together. Check API and worker readiness and queue progress before
   reopening intake.
4. Make sure `PUBLIC_API_URL` is the API's public https address that Microsoft
   Graph can reach, because notifications now always go to `PUBLIC_API_URL`
   followed by `/webhooks/microsoft`. Then create each recorded subscription
   again with `POST /microsoft/subscriptions`, the department's API key and the
   body `{"resource": "<recorded resource>"}`, where the resource is
   `/me/drive/root`, `/drives/{drive-id}/root` or `/sites/{site-id}/drive/root`.
   The new subscription gets a secret, and an old one for the same resource and
   Microsoft connection is retired; Graph lets the old subscription expire. The
   dashboard has no control for this. Until a subscription is created again,
   its notifications are refused and Microsoft changes in that drive queue no
   sync through it. `PATCH /microsoft/subscriptions/{subscription_id}` refuses
   to renew an old subscription with 409, and a webhook refresh job retires it
   instead of renewing it. Deployments that never created a Microsoft
   subscription can skip steps 1 and 4.
5. Callers of `POST /microsoft/subscriptions` that send `notification_url`
   must send the API's own receiver or leave it out, and Microsoft sync folders
   must be added with their Graph item ID. Other values are refused with 422.
6. Recheck source identity, remaining findings and the exact saved output.
   A working file requires separate human approval before publication or
   external writebacks. Unsafe or unsupported output is withheld.

A rollback requires quiescing writers and restoring the matching
**pre-upgrade database**, uploads, artifacts, configuration and encryption keys
with the previous API, worker and dashboard images. Local activity after that
backup is lost; reconcile external writebacks separately. Follow the
[upgrade and recovery procedure](../deployment/upgrade-recovery-rehearsal.md)
and the [v0.9.12 operator notice](v0.9.12.md#operator-action-required).

## Publication integrity

The [release workflow](../RELEASE_INTEGRITY.md) requires this checked-in body
to be consumed verbatim. Publication requires a **signed annotated tag** with a
**GitHub-verified** signature, a successful `ci.yml` push run for the exact
tagged commit on the default branch, and approval through the protected `release` environment.
It must build and verify native `linux/amd64` and
`linux/arm64` API/dashboard images, signed image provenance and signatures,
the CLI through npm trusted publishing, and a seven-file SBOM bundle (three
dependency CycloneDX files and four image SPDX files). The release safety
scan, reviewed vulnerability dispositions and all exact-artifact gates still
apply. Check the workflow result and published artifacts before upgrading.
